# Design-review verdict: compaction replay-run lifecycle (OMN-21090, plan task CM.0)

Verdict: **PASS with conditions.** The replay-run lifecycle and the live kill
switch of the compaction measurement plan (section 3 and section 4, tasks CM.10
and CM.16) may be built against this model under the four conditions below.

Reviewed against the committed TLC output in this directory, bound to
`model.sha256` (the sha256 of `CompactionReplayRun.tla`, then each cfg in sorted

What the model covers, each invariant broken by its own mutant with every
invariant of Model.cfg still enabled:

- one terminal row per run key (case and arm), including a late second writer;
- no arm reads a source record after the boundary instant, and a refused read is a
  terminal `fail`, not a skipped warning;
- an infrastructure fault that survives its retries removes the case from every
  arm, taking back cells an arm had already counted;
- a retried run restores the snapshot, never the dirty worktree of its last attempt;
- a cap stop and an infrastructure fault are different terminal kinds, and a cap
  stop does not remove the case;
- one prefix and one snapshot per case, shared by both arms;
- after two incidents with distinct dedup keys trip the switch, no later session is
  assigned `on`.

Conditions, which are limits of the model that the builders must meet in code or
close by extending the model first:

1. **One case in the bounds.** Two cases did not finish in ten minutes at over a
   million distinct states, because the replay and live sub-machines multiply. Each
   invariant is per case, so one case with two arms exercises each of them, but
   independence between cases is not checked. CM.10 keeps the per-case removal a
   per-case operation.
2. **The trip is atomic with the second incident.** The model flips the switch in
   the same step that records the second distinct key. CM.16 must make counting the
   incident and flipping the arm one write (or fence assignment on a re-read of the
   count); a read-count-then-flip gap is not modelled and would let one more `on`
   in. Block pairing and balance are not modelled either; CM.16's own tests hold them.
3. **The second terminal is a mutation action.** `DuplicateTerminal` is the late or
   redelivered writer that exists only when `UniqueTerminalGuard` is FALSE. The
   guarded model has no such action, so CM.10 must write the terminal as a keyed
   insert that refuses a second row (a unique constraint on the run key), not as a
   check followed by an insert.
4. **Cells are the analysis set.** The model takes a removed case's cells out of
   one `analysis` set. CM.12 must derive inclusion from the terminals and the removal
   list at report time, or delete the cells, with the same result for every arm of
   the case; matched removal is the property, not the storage.

Liveness: `Terminates` (every run key gets a terminal row) holds under weak
fairness of `Next`; retries are bounded by `MaxAttempts`.
